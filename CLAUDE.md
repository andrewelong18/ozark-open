# Ozark Open Sportsbook — Context for Claude Code

Private fantasy-golf betting platform for the annual Ozark Open (Sept 24–26, 2026; app wrapped by Sept 10). Pari-mutuel pool — no house, no rake, no profit. ~32 participants, strictly behind login. Vibe-coded weekend project: prefer the simplest thing that works; no abstraction layers or future-proofing the docs don't ask for.

## Stack (decided — don't relitigate; rationale in docs/ARCHITECTURE.md §2)

Next.js 15 (App Router) + TypeScript · Supabase (Postgres, magic-link auth, RLS) · Vercel (auto-deploy from `main`) · Tailwind + shadcn/ui · Google Sheets API (read-only leaderboard)

## Sprint Workflow ("start sprint N")

1. **Plan.** Read `docs/sprints/sprint-N.md` (self-contained) plus only the `docs/PRD.md`/`docs/DATA_MODEL.md` sections it cites — you should not need the whole `docs/ROADMAP.md` to start. Verify the sprint's blockers are cleared and the prior sprint's "Done when" holds if it's a dependency (read that blocker's `sprint-*.md` if needed). Plan exactly what the sprint's checkboxes list — no scope creep; anything extra becomes a GitHub issue, not work.
2. **Build.** One commit per checkbox-sized task, in checkbox order where dependencies allow. Schema changes only via new files in `supabase/migrations/`.
3. **Verify.** The sprint's **"Done when"** line is the acceptance test. Run it (or the closest local approximation — `npm run build`, unit tests, manual flow) before claiming done. Report failures plainly.
4. **Ship & update status — same commit series, never skipped.** Check off completed tasks in `docs/sprints/sprint-N.md`, then in `docs/ROADMAP.md` flip the sprint's row in the Sprint Index **and** its phase row in the Status Summary (🔲 → 🔶 → ✅) with the date, adjusting target dates if the schedule moved. Both must reflect reality the moment a sprint ships.
5. **Log leftovers as GitHub issues** — never as chat notes or code TODOs:
   ```
   gh issue create -R andrewelong18/ozark-open --title "Sprint N: <thing>" --body "<context + exact steps>"
   ```
   File one issue per item for: bugs found but not fixed, manual steps a human must do outside the repo (Supabase Studio data entry, Vercel/Supabase dashboard config, Resend setup, DNS, asking Pat/Jake something), and out-of-scope discoveries. Title prefix `Sprint N:`; body must be self-contained.

## Project Conventions

- **Migrations only.** Schema changes are SQL files in `supabase/migrations/`; Supabase Studio edits data, never schema.
- **Prod migrations & data edits can be applied directly** when the Supabase MCP is connected (`.mcp.json`, `SUPABASE_ACCESS_TOKEN` set) — use `apply_migration` for a new migration file and `execute_sql` for data edits, then verify. Only fall back to filing a "run this in prod" GitHub issue (step 5) when the token isn't present. Auth-dashboard settings go through `scripts/prod-auth-config.sh`; see `docs/AGENT_AUTOMATION.md`.
- **The bet menu arrives by spreadsheet upload** (`/admin/import`, upsert by the sheet's `bet_id`/`pick_id` — ADR 0001). Studio is the admin CMS for everything else; the custom admin UI is that upload page, the `/admin/people` access console (Sprint 20 — the whole registration funnel with approve/edit/revoke and bulk invite entry, absorbing Sprint 16's `/admin/participants` and Sprint 10's `/admin/roster`, which now redirect to it), and the read-only `/admin/view` View-sheet replica (Sprint 7). **Scope expanded Jul 31, 2026** after the dry run with Pat — the previous "Studio for everything else" line left Pat unable to run the tournament without database access. As shipped, the custom admin surface is five pages: `/admin/import`, `/admin/people` (now also editing display names, #99), `/admin/view`, `/admin/close` (Sprint 25), and `/admin/rules` (Sprint 23, #100). Admins also place wagers for a member at `/bets?for=<userId>` (#101) — every §7 rule evaluates against the **bettor**, never the acting admin, and `bet_placements.placed_by_user_id` records who typed it in (ADR 0001 §13). **Admins can also create a member outright** from `/admin/people` (#124, Aug 9, 2026) — `POST /api/admin/members` makes a real, confirmed auth account with no email sent, so the account is claimable later; approval stays a separate call to `/api/admin/participants`, which owns the entry fee.
- **The app never adjudicates a bet.** Results (hit/miss/push/void) are computed in the admin's Excel workbook and uploaded per pick. Don't build resolution logic.
- **Odds display values come from the sheet** (`fractional_odds`, `probability`, `total_probability` — verbatim, never recomputed). `american_odds` is for payout math only.
- **Validation is server-side** in `lib/validation.ts`, called from API routes. Client checks are UX, not security.
- **A write that matches zero rows is a success, not an error.** PostgREST returns `error === null` when RLS filters an `UPDATE` to nothing, so `if (error)` is not a check — it's how #99 reported "saved" for a month while changing nothing. **Any route updating a row it doesn't own must `.select()` and treat zero rows as a failure.** The RLS policy set is asserted against `supabase/expected-policies.txt` (`scripts/policy-manifest.ts`, run by `local-db-verify.sh`); if you add, remove or re-scope a policy, regenerate it in the same commit with `POLICY_MANIFEST_WRITE=1 bash scripts/local-db-verify.sh`.
- **There is exactly one service-role key, in exactly one module.** `lib/supabase/admin.ts` bypasses RLS entirely and exists solely because an auth account can't be created without it (#124). It has **one** importer — `app/api/admin/members/route.ts` — asserted by `lib/admin-client-containment.test.ts`, not merely documented. Adding a second importer is a security decision, not a refactor: reach for an RLS policy or a `SECURITY DEFINER` function (like `admin_auth_activity()`) instead. Everything else in the app runs on the anon key. See `DATA_MODEL.md` §5.1.
- **Entry collection is recorded, never adjudicated** (Sept 2, 2026 / PRD §12 A17). `tournament_participants.paid_amount` / `paid_at` / `paid_note` record what an admin says came in, edited on `/admin/people`. Two rules, both asserted by `scripts/collection-roundtrip.ts`: it **records** collection and never **decides** the mechanism (still Pat's call — `OUTSTANDING_DECISIONS.md` §3), and it is **never an input to pool math** — an unpaid member still funds the pool on paper, which is why the gap needs showing and why nothing in `lib/payouts.ts` may read these columns. Admin-visible only: `/results` has **no** admin gate, so collection is a separate block behind `viewerIsAdmin()`, never a section inside the settlement text people paste into the group thread.
- **PRD §7 rule 6 is enforced in the database** (Sept 2, 2026 / A18). `enforce_placement_total()` locks the bettor's participant row `FOR UPDATE` and re-sums; the lock is the fix, since re-summing alone fails identically under READ COMMITTED. The TypeScript check in `validateRunningTotal()` stays as the fast, friendly path and the trigger raises its exact sentence. Don't add a second aggregate rule this way without the same treatment — a trigger without a lock is a placebo.
- **`/api/health` runs the reads the app depends on** — the tournaments row, the dashboard's `bets` read including `opened_at`, the collection columns — and answers 503 naming the failure. It exists because on Aug 31 a deploy outran its migration and both Vercel and Supabase stayed green through the outage. Logic in `lib/health.ts` (unit tested); the route is glue. It returns no data — names, booleans and timings only. **The endpoint is UNAUTHENTICATED, so a check earns its place only by meeting both bars: an `anon` caller can get a true answer to it (that means the SCHEMA — RLS filters rows to nothing with no error, and EXECUTE is granted per role), and its failure actually breaks a page.** Both were learned the hard way in production: judging "no tournament row" from an RLS-filtered read pinned it red on every request, and checking `activity_placements()` — granted to `authenticated` only, behind a feed designed to degrade — pinned it red again. Add a check when a page starts depending on a new column; weigh it against both bars first.
- **Payout math:** `placement_payouts_view` computes theoretical payouts **from `odds_at_placement`** (snapshotted at write — never the live pick odds) against each **pick's** result; `lib/payouts.ts` does the proportional split at render with a void-adjusted pool (pool = entry fees − voided stakes).
- **Rule parameters live on the `tournaments` row** — never hardcode entry-fee bounds, pick counts, or caps.
- **Every import takes a save state first, and is refused if it can't** (Sprint 11). `public.take_snapshot()` dumps the five money tables to `snapshots.payload`; `/admin/import` calls it before the first write, there's a Snapshot-now button for hand edits, and `scripts/restore-snapshot.ts <id> --yes` rolls it back in one transaction. Snapshots are the **undo button**; `scripts/db-export.sh` (Sprint 9) is still the **fire escape** and neither replaces the other — see `docs/DATA_SAFETY.md`. Adding a table means adding it to `db-export.sh`'s `TABLES` list, or its guard aborts the backup.
- **Placements are soft-deleted** (`deleted_at`) and odds-snapshotted; money rows keep their history. **Revokes are soft too** (`tournament_participants.revoked_at`, Sprint 21 / PRD §12 A13) — the row carries the entry fee, which is a pool input, so betting eligibility means "a row exists **and** `revoked_at IS NULL`", never bare row-existence.
- **The PRD §7 bet rules, the five-category pick rules (PRD §6), and the §12 decision log (incl. ADR 0001's A1–A10) are settled.** Don't relax, reorder, or reinterpret them without asking.
- **Docs beat code.** When they disagree, flag the drift — don't silently align to the code.

## Out of Scope (don't propose)

Scoring/skins/leaderboard math (stays in the Excel workbook) · bet resolution logic (results come from the admin's workbook per pick — ADR 0001) · **moving** money (Venmo, out of band — recording who has paid is in scope, see below) · public access, SEO · notifications · multi-tenancy · parlays, live odds, cash-out, real-time updates · new bet categories without a code change (by design)

*(Custom admin UI was on this list until Jul 31, 2026 — see the admin-UI note in Project Conventions for what's now in scope and why. "Payments" was narrowed to "moving money" on Sept 2, 2026 — see the entry-collection convention.)*
